Project Overview

Code Editor is a fully-featured desktop IDE built from the ground up with modern web technologies and a Rust-powered native backend. It provides a VS Code-like experience — file explorer, multi-tab editor, integrated terminal, Git integration, GitHub PR/issue management, command palette, and comprehensive theming — all packaged as a native desktop application.

Application Architecture

A layered architecture with clear separation between the native Rust backend, the Tauri IPC bridge, and the React frontend.

📦 Layer 1: Rust Backend

Six Rust modules handle OS operations: filesystem read/write/watch, PTY session lifecycle, Git porcelain commands, full-text search (git-grep or walkdir), shell detection, and event-based filesystem watching. Commands are registered in lib.rs via tauri::generate_handler! and managed as Tauri managed state.

🔗 Layer 2-3: Tauri IPC

TypeScript wrappers in src/tauri/ abstract the invoke() calls to Rust commands with full typing. Each wrapper function maps to one Tauri command, ensuring type-safe communication. Event listeners capture filesystem changes and PTY output via Tauri's event system.

🧠 Layer 4: State Stores

Seven Zustand stores with persistence middleware separate concerns: fileStore (file tree + folder state), editorStore (tabs + Monaco models), terminalStore (PTY sessions), gitStore (Git operations + status), githubStore (OAuth + API data), uiStore (panel sizes + theme), settingsStore (user preferences).

🎨 Layer 5: React UI

The component tree mirrors VS Code's layout: a shell with custom title bar, menu bar, activity bar, resizable sidebar, editor area, bottom panel with tabs (terminal/problems/output/debug), and a status bar. Lazy-loaded MonacoEditor, React portals for modals, and shadcn/ui primitives throughout.

Backend Architecture

Six Rust command modules, each responsible for a distinct OS-level capability, exposed via Tauri's invoke handler.

📁 fs.rs — File System

walkdirdirsstd::fs

Provides 11 commands: read_directory (recursive walking with depth control and hidden file filtering), read_file, write_file (auto-creating parent directories), create_file (exclusive creation), create_directory, rename_entry, delete_entry (recursive for directories), resolve_home, stat (symlink-safe metadata), path_exists, and reveal_in_explorer (cross-platform OS file manager opening).

🖥️ pty.rs — Terminal/PTY

portable-ptystd::thread

Manages the lifecycle of pseudo-terminals via the portable-pty crate. spawn_pty creates a new PTY session for a given shell path, spawns a reader thread that emits terminal:stdout:{id} events, and stores the writer/killer handles in a HashMap<String, PtyHandle> wrapped in Arc<Mutex>. write_pty writes stdin, resize_pty adjusts terminal dimensions, and kill_pty terminates the child process and cleans up the session. Exit events are emitted as terminal:exit:{id}.

🔀 git.rs — Git Integration

std::process::Command

Implements 26 Git porcelain commands by shelling out to the system git binary. All commands parse --porcelain=v2 output for structured status reporting. Key commands: git_status (parses staged/unstaged/untracked/conflicted), git_diff, git_log (with format options), git_branch_list/create/delete/checkout, git_add/reset/commit, git_push/pull/fetch (with secure token injection via GIT_CONFIG_PARAMETERS environment variable), git_stash_*, git_blame (porcelain format), git_remote_*, git_submodule_status, git_init, git_config_get/set, git_is_repo, and git_merge_base.

👀 watch.rs — File Watcher

notifytauri::Emitter

Wraps the notify crate's RecommendedWatcher for recursive filesystem monitoring. watch_directory starts watching a path and emits fs:change Tauri events with the root, kind (create/modify/remove), and affected paths. unwatch_directory and unwatch_all clean up watchers. The frontend listens for these events to trigger debounced tree refreshes and detect external file modifications in open tabs.

🔎 search.rs — Full-Text Search

git grepwalkdir

Adaptive search: if the root is a Git repository, delegates to git grep for speed (with case-sensitivity, whole-word, regex, include/exclude pattern options). Otherwise falls back to a pure Rust walkdir-based search that reads each file and performs substring matching. Results are capped at a configurable maxResults (default 1000). Returns structured SearchMatch objects with path, line, column, content, and match length.

🖥️ shell.rs — Shell Detection

std::env

Cross-platform shell detection. On Windows: enumerates PowerShell 7, Windows PowerShell, Command Prompt, and WSL (if available) via PATH lookup. On Unix: parses /etc/shells, prioritizes the $SHELL environment variable, and validates that each path exists. Returns structured Shell objects with id, label, path, and arguments for the frontend's shell picker.

The Editor in Detail

How the Monaco editor is configured, themed, and integrated with the state store for a seamless editing experience.

⚡ Monaco Editor Setup

monaco-editor 0.55@monaco-editor/react 4.7

The editor is initialized in src/lib/monaco-setup.ts where MonacoEnvironment.getWorker is configured to load language-specific web workers (json, css, html, typescript) for syntax highlighting and IntelliSense. Three custom themes are defined: code-editor-dark (GitHub dark #0d1117 background), code-editor-light (white background), and code-editor-catppuccin (Catppuccin Mocha palette).

const setupMonaco = (): void => {
  const w = window as unknown as { MonacoEnvironment?: { getWorker: (...) => Worker } };
  w.MonacoEnvironment = {
    getWorker(_workerId, label) {
      switch (label) {
        case "json": return new jsonWorker();
        case "typescript": case "javascript": return new tsWorker();
        default: return new editorWorker();
      }
    },
  };
  monaco.editor.defineTheme("code-editor-dark", DARK_THEME);
};

📑 Tab & Content Management

editorStore.tsZustand persist

The editorStore manages open tabs as an ordered array of Tab objects. Each tab tracks: path, name, language, isDirty, savedContent, currentContent, and cursor position. Opening a file reads its content via Tauri's read_file invoke, creates a tab, and inserts it adjacent to the active tab. The saveFile action optionally formats on save using Monaco's format action, then writes via write_file. An epoch-based deduplication system prevents redundant external-change handling after saves.

🔄 External Change Detection

The useFileChangeSync hook listens for fs:change Tauri events. When a change is detected for a currently open file, handleExternalChange in the editor store reloads the file content from disk — but only if the tab is not dirty and the last save epoch has passed. This prevents overwriting unsaved work while keeping the editor in sync with external modifications (e.g., from Git operations or other editors).

💾 Session Restore

session.ts

On startup, App.tsx calls loadSession() from src/lib/session.ts to restore previously open tabs with their cursor positions. The session is auto-saved to localStorage on every tab change via a Zustand subscription. A separate unsaved backup mechanism stores dirty file contents (capped at 1MB) as a safety net against data loss. Recent folders are tracked using a capped list (max 10) shown on the Welcome page.

File System Explorer

How the file tree is built, filtered, and interacted with — from the Rust backend to the React tree component.

🧵 Web Worker for Tree Building

fileTree.worker.ts receives raw FileEntry[] and a .gitignore string, parses the gitignore into glob rules, builds a hierarchical tree structure, filters out ignored and hidden files, and returns sorted FileNode[]. This offloads the computationally expensive tree construction from the main thread, keeping the UI responsive even in large directories.

📋 Context Menu Operations

The useExplorerActions hook provides file/directory operations via the Rust backend: createFile, createFolder (both validate names for path separators/null bytes), rename (with state migration for expanded directories and selections), delete (recursive for directories), and moveItem (rename-based drag-and-drop). All operations refresh the tree after completion.

🔄 Filesystem Watching

When a folder is opened, setupWatcher registers a recursive notify watcher on the root directory. Changes emit fs:change Tauri events, which trigger a debounced (200ms) tree refresh in the fileStore. The watcher is torn down when closing the folder via teardownWatcher. Custom ordering of items is persisted in localStorage.

🖱️ Drag & Drop

The file tree uses @dnd-kit/core and @dnd-kit/utilities for reordering items within directories via drag-and-drop. The reorderItems action persists the custom order. Cross-directory moves use the moveItem action which performs a rename_entry on the backend. The DirDropTarget component provides visual drop zones.

Integrated Terminal

A full pseudo-terminal integrated into the editor, backed by Rust PTY sessions and rendered with xterm.js.

🔄 PTY Lifecycle

When createSession() is called: (1) shells are detected if not loaded, (2) the default shell or specified shell is selected, (3) a UUID session ID is generated, (4) Tauri event listeners for terminal:stdout:{id} and terminal:exit:{id} are registered, (5) spawnPty is invoked to create the native PTY via portable-pty, (6) a Rust reader thread emits stdout data as events, and (7) the session is added to the store with its output buffer. Sessions are capped at 8 maximum.

💾 Output Buffering

Each session has a SessionOutputBuffer with a ring buffer (max 5000 lines) that stores all output as strings. The attachToSession method lets components subscribe to real-time output. A terminal.worker.ts web worker batches writes to xterm.js for performance: output chunks are accumulated and flushed every FLUSH_INTERVAL_MS (default 16ms ≈ 60fps), reducing DOM updates and preventing xterm from being overwhelmed during rapid output.

🎨 Theming & Resizing

The useTerminalTheme hook maps the app's three themes (dark, light, catppuccin-mocha) to custom xterm.js color palettes, including 16 ANSI colors plus cursor and selection colors. The FitAddon auto-sizes the terminal to fill its container. A ResizeObserver defers reflow via requestAnimationFrame to avoid layout thrashing, and the new dimensions are sent to the Rust backend via resize_pty.

📋 Multiple Sessions & Tabs

The bottom panel supports multiple terminal sessions with tabbed navigation (TerminalTabs), each labeled sequentially (shell-1, shell-2, ...). A shell picker dropdown allows choosing between available shells (PowerShell, CMD, WSL, bash, zsh, etc.). Sessions can be renamed, killed, and cycled through. A context menu provides additional operations. The terminal tab bar sits alongside Problems, Output, and Debug Console panels.

Git Integration

Full source control management — 27 Git commands explained simply, from how they work to why they exist.

📖 Git in Plain English

Think of Git as a time machine for your code. Every time you make a change you want to keep, you take a "snapshot" (called a commit). These snapshots form a timeline you can travel back and forth on. You can also create branches — like alternate universes — where you can try new things without messing up the main timeline. The editor has 27 commands that control this time machine, and here's what each one does:

📸 Commit = A snapshot 🌿 Branch = An alternate timeline 📦 Repository = Your project folder 🌐 Remote = A copy on GitHub

🔍 Automatic Git Detection

When you open a folder, the editor automatically checks: "Is this a Git project?" It does this by running a quick check to see if a hidden .git folder exists. If yes, it immediately loads your current status, branches, remotes (like GitHub), stashes, and even reads your Git username and email. You don't need to do anything — it just works. If the folder isn't a Git project yet, a button appears to let you init (start tracking).

🔐 Secure Authentication

When you push code to GitHub, the editor needs to prove who you are. Instead of typing your password insecurely, the editor uses a secret token (like a digital key). This token is passed to the Rust backend, which feeds it to Git through a hidden environment variable — never visible on screen or in command logs. This keeps your credentials safe from other programs running on your computer.

⚡ Smart Caching (Web Worker)

Checking Git status can be slow on large projects. The editor runs Git commands in a background web worker (like a helper that works in the background without slowing down the UI). It also uses a smart cache — if you check status multiple times within 5 seconds, it reuses the last result instead of re-running the command. Think of it like remembering the answer instead of re-calculating every time.

📊 Understanding Status

The status command is the most important — it's like a dashboard showing what's happening. It tells you: which branch you're on, how many commits ahead/behind the remote you are, which files are staged (ready to commit), which are unstaged (changed but not ready), which are untracked (new files Git doesn't know about), and which have merge conflicts. The editor parses Git's machine-readable output into a clean, structured format the UI can display.

📋 All 27 Git Commands — Explained Simply

📊 status

Dashboard

What it does: Shows you the current state of your project — which files have changed, which are ready to save (staged), and which branch you're on.

Real-world analogy: Like looking at a checklist to see what's been done, what's half-done, and what hasn't been started yet.

📝 diff

Compare

What it does: Shows exactly what lines you added, removed, or changed in a file, line by line. Green is new, red is removed.

Real-world analogy: Like comparing two versions of a document with "track changes" turned on.

📜 log

History

What it does: Shows the complete history of commits (snapshots) for your project — who made each change, when, and what they wrote about it.

Real-world analogy: Like flipping through a photo album of your project, where each photo has a date and a caption.

🌿 branch_list

List timelines

What it does: Lists all branches (alternate timelines) in your project — both local (on your computer) and remote (on GitHub). Shows which one is active and how ahead/behind each branch is compared to others.

🌱 branch_create

New timeline

What it does: Creates a new branch so you can work on a feature or fix without affecting the main code. It's like forking off into a parallel universe where you can experiment freely.

Real-world analogy: Like making a copy of a document to try wild edits while keeping the original safe.

🗑️ branch_delete

Delete timeline

What it does: Deletes a branch you no longer need. Usually done after the feature is finished and merged into the main branch. Optionally can force-delete even if the branch hasn't been merged.

🔄 checkout

Switch timeline

What it does: Switches your active branch — like stepping into a different timeline. All your files automatically change to match that branch's version.

Real-world analogy: Like pressing a button that transforms your workspace to match whatever branch you select.

➕ add (stage)

Prepare to save

What it does: Tells Git "I want to include this file in my next snapshot." This is called staging — it lets you carefully choose which changes to commit.

Real-world analogy: Like putting files into a box before sealing it. You can add or remove files before you finally close the box (commit).

⏪ reset (unstage)

Remove from box

What it does: The opposite of add — removes files from the "staging area" so they won't be included in the next commit. Your file changes are preserved, just not marked for the snapshot.

📸 commit

Take a snapshot

What it does: Takes a permanent snapshot of all staged files. You must write a message describing what you changed. Git records who made it, when, and exactly what the code looked like at that moment. Returns a unique ID (hash) for this snapshot.

Real-world analogy: Like pressing the shutter button on a camera — it freezes your code in time forever.

📤 push

Upload to cloud

What it does: Uploads your local commits to GitHub (or another remote server). Once pushed, others can see your changes. Supports force-push (with safety checks) and setting upstream tracking.

Real-world analogy: Like saving a document from your computer to Google Drive so others can see it.

📥 pull

Download from cloud

What it does: Downloads the latest changes from GitHub and merges them into your current branch. Supports rebase mode and fast-forward-only mode for cleaner history.

Real-world analogy: Like syncing a shared Google Doc to get everyone's latest edits.

👀 fetch

Check for updates

What it does: Checks what's new on GitHub without actually merging anything. It's like peeking at what others have pushed — you can decide later whether to pull those changes. Supports pruning deleted branches and fetching tags.

Real-world analogy: Like looking at what's in the fridge before deciding what to eat — you're just gathering information.

🔗 remote_list

View connections

What it does: Lists all remote servers (like GitHub, GitLab) that your project is connected to. Shows both the URL used for downloading (fetch) and uploading (push).

🔗 remote_add

Add connection

What it does: Connects your local project to a remote repository (e.g., on GitHub). You give it a name (usually "origin") and the URL. After this, you can push and pull.

🔗 remote_remove

Remove connection

What it does: Disconnects from a remote server. The local code stays untouched — it just removes the link to that external repository.

📦 stash_list

View temporary saves

What it does: Lists all your saved temporary changes (stashes). Each stash shows its index number, the message you gave it, the branch it was made on, and its unique hash.

📦 stash_push

Temporarily save

What it does: Temporarily puts aside any uncommitted changes — like hitting "pause" on your work. This is useful when you need to switch branches urgently but aren't ready to commit yet.

Real-world analogy: Like clearing your desk into a drawer because you need to work on something else. You can pull everything back out later.

📦 stash_pop

Restore temporary save

What it does: Restores the most recent stashed changes (or a specific stash) back into your working files and removes it from the stash list. Like taking your stuff back out of that drawer.

📦 stash_drop

Discard temporary save

What it does: Deletes a stash that you no longer need. If you restored your changes and everything is fine, you can drop the backup.

🔍 blame

Find who wrote what

What it does: Goes through every line of a file and shows who last changed it, when they changed it, and in which commit. Each line gets annotated with the author, date, and commit message.

Real-world analogy: Like looking at a whiteboard and seeing each person's handwriting color-coded with their name and the time they wrote it.

📦 submodule_status

Check sub-projects

What it does: A submodule is like a project inside your project (e.g., a library you imported). This command shows the status of all submodules — their paths, URLs, current commits, and whether they have uncommitted changes.

🚀 init

Start tracking

What it does: Turns a regular folder into a Git repository. It creates a hidden .git folder that will track every change you make. You only do this once per project, at the beginning.

Real-world analogy: Like installing a security camera system in your house. After setup, everything is recorded.

⚙️ config_get

Read settings

What it does: Reads Git configuration values — like your name, email, or preferred editor. It checks the local project settings first, then falls back to global settings if not found.

⚙️ config_set

Write settings

What it does: Changes Git configuration values. You can save settings locally (for just this project) or globally (for all your Git projects). Used to set your name, email, or other preferences.

✅ is_repo

Quick check

What it does: A simple yes/no check: "Is this folder a Git repository?" It runs git rev-parse --git-dir which quickly returns success if a .git folder exists, or fails if not.

🔀 merge_base

Find common ancestor

What it does: Finds the most recent commit that two branches share in common — their "common ancestor." This is used to understand where two branches diverged, which is critical for calculating diffs and resolving merges.

Real-world analogy: Like finding the last photo two siblings appear in together before they went their separate ways.

🦀 How the Rust Backend Runs Git

The Rust code in src-tauri/src/commands/git.rs (616 lines) handles all Git operations. Instead of using a Git library, it directly runs the git command on your system, just like you would in a terminal. Here's how a typical command flows:

Step 1: Frontend calls invoke("git_status", { root: "/my/project" })
Step 2: Rust runs on your computer: git status --porcelain=v2 --branch
Step 3: Rust parses the machine-readable output line by line
Step 4: Extracts branch name, ahead/behind counts, staged files, unstaged files, untracked files, and conflicted files
Step 5: Returns a structured GitStatus object to the frontend

For push/pull/fetch with authentication, the GitHub token is passed securely through the GIT_CONFIG_PARAMETERS environment variable rather than command-line arguments (which other processes on your computer could see). This uses the format http.extraHeader=Authorization: bearer {token}.

GitHub Integration

OAuth-based GitHub authentication with PR and issue tracking, directly inside the editor.

🔑 OAuth Device Flow

Authentication uses the GitHub OAuth Device Authorization Flow via @octokit/auth-oauth-device. When the user clicks "Sign In", the app requests a device code from GitHub. The user is shown a verification code and a URL (github.com/login/device). Once they enter the code, the app polls for an access token. The token is persisted in localStorage alongside the authenticated user's profile (login, avatar, name, email). Token restoration is attempted on rehydration.

📦 Octokit REST Client

The @octokit/rest library provides the API client. It's initialized once (createOctokit) with the OAuth token and destroyed on sign-out (destroyOctokit). The client fetches: open pull requests (with check run statuses via checks.listForRef), open issues (filtered to exclude PRs), and the remote repository info is parsed from Git remotes via parseGitHubRemote (supports both HTTPS and SSH URL formats).

🔍 PR & Issue Views

The GitHub panel shows two tabs: Pull Requests and Issues. Each PR card displays: number, title, author avatar, draft/merged status, labels, and CI check status indicators (success/failure/pending). Clicking a PR opens a detail view with the full description and check runs. Issues show similar info with comment counts. The GitHubPullRequestDetail component renders PR metadata with check status badges.

🔗 Remote Detection

The setRepoFromRemote action automatically detects the GitHub repository from the "origin" Git remote. It parses the remote URL (HTTPS: https://github.com/owner/repo or SSH: git@github.com:owner/repo) to extract the owner and repository name. This links the authenticated session to the current project's GitHub context.

Data Flow

How data moves through the application — from user interaction to the Rust backend and back to the UI.

📡 Event-Based Communication

The Rust backend emits Tauri events for asynchronous push-based communication:

  • • fs:change — Filesystem changes (create/modify/remove)
  • • terminal:stdout:{sessionId} — PTY output data
  • • terminal:exit:{sessionId} — PTY process exit with code/signal

The frontend subscribes to these events via @tauri-apps/api/event listen() in the corresponding stores, enabling reactive UI updates without polling.

🧠 Web Workers

Three web workers offload CPU-intensive work from the main thread:

  • • fileTree.worker.ts — Builds hierarchical file trees from flat entry lists, applying .gitignore rules
  • • git.worker.ts — Caches and processes Git data with LRU cache
  • • terminal.worker.ts — Buffers and throttles xterm.js writes to 60fps

All workers communicate via structured postMessage with a request/response protocol using UUID-based correlation IDs.
